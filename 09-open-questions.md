# 09. Decision log

This is the plan's decision log: 45 numbered decisions, each with the question it answers,
the decision and the files that apply it. The numbers are stable identifiers cited
throughout the plan, so they are never reused or renumbered. Decisions 4, 18 and 21 are
superseded by decision 25 and kept only so the numbering stays stable; every other row
states the decision in its final form.

The groups below follow the order in which the questions arise when the plan is read
front to back: scope and foundations, shared code and lifecycle, module layout, delivery
structure and SDK contracts, releases and examples, and finally the quality gates and the
public API.

## Module and versioning

| # | Question | Decision | Where applied |
| --- | --- | --- | --- |
| 25 | Versioning of the components | **One module, one version.** The repository publishes a single Go module `github.com/<owner>/powertools-lambda-go` (`<owner>` is a placeholder) with a single tag `vX.Y.Z` for every package; no per-utility modules, no shared `internal` module, no lockstep tagging, no `go.work`. Tags are cut by semantic-release, counting from a seed tag `v0.0.0` (decisions 27 and 34). `examples/` is an untagged module with a `replace` to the parent. Accepted cost: the X-Ray SDK is in every consumer's module graph, never in logger-only binaries. The `deps` CI job enforces this with a direct and a transitive import rule, both on production code only (decision 31). Supersedes 4, 18 and 21. | 01 §2, 04 §1, 05, 06 §5 and §6, 07, 08, 11, README |

## Delivery structure and SDK contracts

These decisions pin the SDK behaviours and the repository tooling the design depends on;
item 2 of the roadmap's [Delivery guidance](07-roadmap.md#delivery-guidance) says to
re-verify each against the pinned SDK versions before Phase 0.

| # | Question | Decision | Where applied |
| --- | --- | --- | --- |
| 26 | Repository tooling | **A `Makefile` is the single interface for every check**: each CI step calls a `make` target, and `make checks` runs every static check CI runs, so a laptop and CI give the same verdict. Test files may carry a build tag (for example `//go:build unit`) so a plain `go build` never compiles test helpers; if they do, every tool receives the tag, allocation-budget files carry `unit && !race`, the real-AWS harness has its own tag and the example files stay untagged (decision 38). Without such a convention the plan works the same untagged. | 06 §1 and §4, 10, 11 §2 |
| 27 | Release and versioning | **Releases are cut by semantic-release from conventional commits** on every push to `main` that changes code, after the tests and static checks run again. No hand-maintained `CHANGELOG.md`, no release target, nothing tagged or pushed to `main` by hand. The release timing is decision 34 and the enforcement decision 40. After `v1.0.0` a breaking change requires a `/v2` module path. | 06 §6, 07, 11 |
| 28 | Delivery structure | **Phase 1 is the API-freeze point.** It writes the final exported signatures of `logger`, `metrics` and `tracer` that the wrapper uses as documented no-op stubs, adds the X-Ray SDK to `go.mod`, writes the complete `State`, and implements `begin`/`end` in full. Phases 2, 3 and 4 fill in only their own package bodies and add wrapper tests in their own root files (`wrap_logger_test.go`, `wrap_metrics_test.go`, `wrap_tracer_test.go`), so they merge in parallel. Phase 0 creates only `examples/bare`; the coverage gate blocks from Phase 0. The real-AWS checks are an optional manual step (Phase 5b, decision 45) and block nothing. | 06 §1 and §5, 07 |
| 29 | `WrapHandler` contract | **Only for hand-written `lambda.Handler` implementations that own the bytes they return.** `lambda.NewHandler(fn)` is not supported: under `MaxConcurrency` above 1 its `Invoke` returns bytes from a pooled buffer already released, a race that `bytes.Clone` does not fix. `WrapHandler` works on the raw payload and response bytes, passing them as `jsontext.Value` to the correlation-ID options and to response metadata. Other handler shapes use `Wrap` with a one-line closure; no adapter API in v1. | 01 §4.2 and §4.3, 02 §8, README |
| 30 | Trace header source | **The only source is `ctx.Value("x-amzn-trace-id")`**, set by `aws-lambda-go` on every invocation. No `_X_AMZN_TRACE_ID` fallback and no `os.Getenv` per invocation; a missing value means "no trace" for logger and tracer alike. Tests set the key through one helper with the single SA1029 suppression. The parse agrees with the SDK's `header.FromString` on `Root`, `Parent` and `Sampled` (decision 35) and keeps the unparsed trailing fields (`Rest`, a zero-alloc substring), so `tracer.Header` forwards fields such as `Lineage`. | 01 R2 and §4, 04 §2 and §7, 06 §1 |
| 31 | Tracer nil-safety and helpers | **`*xray.Segment` methods are not nil-safe** (only `Close` is), so the tracer adds nil-safe helpers `AddAnnotation(ctx, key, value) error`, `AddMetadata(ctx, key, value) error` and `InstrumentAWS(apiOptions)`. `end()` nil-checks the segment before every SDK call; the handler segment stays in a local variable of the wrapper, never in `State`; the open-subsegment warning checks after `Close(err)` whether the SDK emitted the handler segment. The import rule covers production code only: test files may import the SDK. Without the wrapper, `Capture` and `CaptureResult` run `fn` untraced when ctx holds no segment and no trace header. `Capture`'s error path adds metadata only; fault and cause come from `Close(err)`. The library never mutates SDK globals, and consumers call `xray.ContextWithConfig` once at init, never per invocation. | 01 §2, §4 and §7, 04 §3 to §8, 06 §1 and §4, 08 §1 |
| 32 | Metrics lifecycle API | **`(*Metrics).EmitColdStart(functionName) error` is exported** (`function_name` from the option, then `POWERTOOLS_METRICS_FUNCTION_NAME`, then the argument). `RaiseOnEmptyMetrics` is a field of `metrics.Options`; under the wrapper a `Flush` error becomes the invocation error only if the handler succeeded, otherwise it is logged at `WARN`. `Flush` returns only sentinel errors, never an I/O error. A batch is empty only if it never held a value, so an auto-flush or a `DeadlineMargin` snapshot that already wrote every value does not make the final `Flush` fail (a documented difference from Python). `FlushSnapshot` writes, then clears metric values and keeps dimensions, metadata and the open state. Key collisions follow Python's merge order (dimensions, metadata, metric values, last wins) in a merge step before encoding, so the encoder never sees duplicate names. A metadata value that fails to marshal is dropped with one `WARN` per batch. | 01 §4 and §6, 03 §2 to §8, 07 Phase 3 |
| 33 | Logger and wrapper structure | **The handler follows slog's `commonHandler` structure** (top-level attrs, grouped prefix, trailing empty groups opened only when a record attr renders). Package functions `Trace`…`Fatal` build the record themselves so `location` names the caller. Duplicate keys are emitted as slog does, and every decoder allows duplicate names and invalid UTF-8. `ReplaceAttr` never sees built-in keys, Lambda keys or `AppendKeys` attrs. `KindAny` values that fail to marshal render as `"!ERROR:<err>"`, like `slog.JSONHandler`; the line is never dropped. `LevelSilent` wins over sampling, and there is no `RefreshSampleRate` (sampling needs the wrapper). `FlushOnErrorLog` is a `*bool` and `BufferAtLevel` a `slog.Leveler`, so zero values stay usable. One shared stdout writer is used when a utility's `Writer` is nil. `logger.FromContext` falls back to `slog.Default()`. Environment reading lives in `internal/lambdaenv`; `internal/jsonpath`, `internal/benchutil` and `internal/testsupport` complete the layout. The tracer's metadata guard is a per-invocation budget counted as escaped size, because the SDK streams by subsegment count, not by size, so an oversized document would be dropped whole. | 01 §2 to §6, 02, 03 §2, 04 §1, §2 and §5, 05 §3 and §4, 06 §1 |

## Releases, environment and examples

| # | Question | Decision | Where applied |
| --- | --- | --- | --- |
| 34 | Release timing and v0 versions | **Release from the start, in v0, and cut `v1.0.0` once at the end.** A seed tag `v0.0.0` makes semantic-release count from v0; the release workflow lands right after Phase 0. Each phase that merges `feat` commits releases a v0 minor; fixes give patches. During v0 an exported API may change, written as `feat` or `fix`, never as a breaking change. After the API review, one commit with a `BREAKING CHANGE` footer cuts `v1.0.0`; v0 to v1 needs no `/v2` path. README install examples use `@latest`. | 06 §6, 07, 08 §3, 11, README |
| 35 | Environment, trace header and wrapper details | (1) **No init-time environment snapshot**: constructors read the environment and cache it, so nothing reads it per invocation and tests can `t.Setenv` before constructing. `InLambda` is `AWS_LAMBDA_FUNCTION_NAME` non-empty; `AWS_LAMBDA_MAX_CONCURRENCY` is read by `aws-lambda-go` only. (2) **Trace header parsing** agrees with the SDK on `Root`, `Parent` and `Sampled` (any position, a later duplicate wins, `Sampled` true only for `Sampled=1`); `Rest` is the trailing run of other fields, an accepted divergence because Lambda sends extra fields last. (3) **The margin timer** is not armed when `remaining - margin <= 0`. (4) **`RemainingTime`** without a deadline returns the maximum `time.Duration` (no limit), so `context.WithTimeout(ctx, RemainingTime(ctx) - margin)` works in local runs and tests; with a deadline it is clamped at 0. (5) **Handler name** under `WrapHandler` is the dynamic type of `h`; `Options.HandlerName` replaces the derived name and `"## "` is always prefixed. (6) **Wrapper edge cases**: a malformed `CorrelationIDPath` is reported once at `WARN` at wrap time and disables the extraction; a panic in `CorrelationIDFunc` is not recovered; a panic in the event's marshal method is recovered and logged. (7) **`Flush` errors** follow decision 32's rule. (8) **`go.mod`** carries an explicit indirect floor on `golang.org/x/net` while the version the X-Ray SDK requires fails `govulncheck`, removed once an SDK release requires a fixed version. | 01 §1 to §7, 02 §1, §8 and §9, 03, 04 §1 to §5, 05, 07 Phase 1, 08 §1 |
| 36 | Metrics behaviour | `New` validates and returns an error (decision 44); an invalid namespace returns `ErrNamespaceMissing` from `New` and `Single.Emit`. `service` is the first default dimension, so it is in every set, every `Single` and the cold-start blob. An auto-flush without a namespace drops its values and `Add` returns `ErrNamespaceMissing`; write errors are logged at `DEBUG` once per batch and never returned by batch paths. Metadata keys `""`, `"_aws"` and invalid UTF-8 are dropped with the one metadata `WARN`. `Len` counts the distinct definitions held and not yet written. Metric names are 1 to 255 printable ASCII bytes, not blank, not `_aws`. At most 29 dimension keys per set, `service` included. Zero values of `Metrics`, `Batch` and `Single` are inert. | 03 §1 to §8 |
| 37 | Examples and real-AWS harness | (a) The `size` job is blocking from its creation: `examples/hello` adds less than 1 MiB over `examples/bare`, both built in the same run (no committed baseline), and `hello` does not reach the X-Ray SDK (`go list -deps` and `go version -m`). (b) SAM templates deploy the prebuilt `bootstrap` (no `sam build`), so the deployed binary is the one the size gate measures. (c) The integration harness is Go tests in `examples/integration` behind `//go:build integration`; without its variables or AWS credentials every test skips, unless a "required" variable is set, and a pull-request step proves the skip. (d) The harness and the Lambda-level measurement are run by hand, through `make` targets, with the developer's own AWS credentials; CI holds no AWS credentials and runs neither (decision 45). (e) The benchmark is two binaries, plain and wrapped, so the init comparison includes linking. (f) `govulncheck` covers the library module only; the never-released `examples` module is covered by dependency updates, so an advisory in an AWS service client never blocks an unrelated library change. (g) SAM templates are linted with `cfn-lint`, limited by a path filter. (h) Example-only changes use `chore(examples)` or `test(examples)`, because the release rules have no scope filter. | 05 §5 and §6, 06 §1, §4 and §5, 07 Phase 5 |

## Quality gates and API

| # | Question | Decision | Where applied |
| --- | --- | --- | --- |
| 38 | Build tag of the example files | **`example_test.go` files carry no build tag** when the repository tags its test files: `go doc -ex` does not list examples from tagged files, and `go doc` has no `-tags` flag. A doc check proves for each public package that `go doc -ex` lists at least one example, that an untagged `go vet` compiles the example files on their own (so an example cannot use a helper of a tagged test file), and that no stub sentence from the API-freeze phase remains. | 05 §5, 06 §1, §4 and §7, 08 §3, 10 |
| 39 | Bench gate | **The bench job blocks and is required once the budgets are locked** (report-only before). One job on one runner checks out the merge base and the head and runs the gated subset of both, interleaved, with `-count 10 -benchtime 300ms -cpu 1`; `benchstat -format csv` feeds a gate script (benchstat always exits 0), which a local target runs too. Any `allocs/op` or `B/op` increase at p < 0.05 fails; `ns/op` fails above 25 % at p < 0.05, smaller deltas are reported. Benchmarks on one side only are `new` or `removed`, never gated; `b.ReportMetric` units are informational. A reviewed accept-list turns a listed failing benchmark into `accepted`; a stale entry is reported. No committed baseline is a gate input; profiles and bench files are uploaded as job artifacts. | 05 §5 and §6, 06 §5, 10 |
| 40 | Release commit and breaking-change guard | **A bang header is banned everywhere**: the angular parser has no `!` in its header pattern, so such a commit releases nothing and leaves the release notes. Its note pattern is case-insensitive and applies to every line of every commit, merge commits included, so nothing starts a line with the breaking-change phrase except the release commit. A guard script scans the pull-request range and the PR title (a squash merge can make the title the header), and, before every release, the range since the highest reachable version tag. The `v1.0.0` commit is accepted once, while no v1 tag exists; after it, a note is accepted only from a commit whose own `go.mod` declares the next `/vN` path. A note commit reverted in the same range, or an allow-listed full SHA, is cleared. The release pull request is merged with a merge commit, not squashed. Recovery when the guard holds `main`: revert the commit that carries the marker (not the merge commit) before any other releasing change; disabling the guard is not a recovery. | 06 §5 and §6, 07 |
| 41 | `v1.0.0` and the real-AWS checks | **`v1.0.0` does not wait for real-AWS checks.** Cutting the release needs no AWS account. The CloudWatch and X-Ray acceptances of Phases 3 and 4 and the Lambda-level measurements of 05 §5 are recorded whenever someone runs the manual harness (Phase 5b, decision 45); a failure found there is a v1 `fix`. | 05 §5, 07 |
| 42 | `Options.LogEvent` | **`powertools.Options.LogEvent` is a `*bool`.** Nil means `POWERTOOLS_LOGGER_LOG_EVENT`; `new(true)` or `new(false)` wins over the variable, so `new(false)` switches a truthy variable off. A plain `bool` could only switch the feature on, which would make it the one environment-backed option that is not tri-state (08 §4). | 01 §3 and §4, 02 §8, 08 §4, README |
| 43 | Metric storage resolution | **No exported resolution type.** The storage resolution is chosen by the method (`Batch.Add`, `Batch.AddHighResolution`, `Single.HighResolution`), so a `Resolution` type with `Standard` and `High` constants stays unexported: no exported function or method would take or return it, and `v1.0.0` would freeze surface nobody can use (08 §4). | 03 §1, §2 and §4, 08 §4 |
| 44 | Deliberate asymmetries in the API | (1) `metrics.New` returns an error while `logger.New` and `tracer.New` do not: metrics validates at construction because an invalid namespace or dimension would make every later blob invalid; the logger falls back with one `WARN`, and the tracer has nothing that can fail. (2) The end-of-handler helper is exported as documented wrapper plumbing: it takes an `*xray.Segment`, and `internal/...` must never reach the SDK. (3) `logger.Handler`, `metrics.Batch` and `metrics.Single` are handed out only as pointers, and no doc promises that their values are comparable, so their fields may hold slices, maps and functions. (4) The three `FromContext` functions share one name, `(*XRayLogger).Log` keeps the SDK's signature, and `RemainingTime` returns the maximum duration without a deadline. | 08 §4 |
| 45 | Docs-only changes and the real-AWS harness | **(a) Docs-only changes skip the code checks and never release.** A first CI job lists the files the pull request changes; the test, lint, deps, size and bench jobs run only when some file is neither Markdown nor under `docs/`, and a diff that cannot be computed runs every job. GitHub counts a skipped job as passed for a required check, so a docs-only pull request stays mergeable. A title or description edit re-runs only the checks that read the title (the breaking-change guard). The release workflow ignores pushes to `main` that touch only Markdown and `docs/`; a `feat` or `fix` commit that touches only those files is not lost, it releases with the next push that changes code, because semantic-release reads every commit since the last tag. **(b) The real-AWS harness is manual and optional.** The integration harness and the Lambda-level measurement stay in the repository as `make` targets that someone runs by hand with their own AWS credentials against SAM-deployed example stacks; no CI workflow runs them, CI stores no AWS credentials, and there is no scheduled workflow. A pull-request step still proves the harness skips without its variables. Phase 5b is this manual run, not code: the CloudWatch and X-Ray acceptances and the measurements of decision 41 are recorded when it happens, and a failure there is a v1 `fix`. | 05 §5, 06 §1 and §5, 07 Phase 5 |
